# 架构与关键决策

> **TL;DR**：插件分**两个半**（Host 半做判定与投递，客户端半只画界面并调 RPC）；
> 渠道是**纯函数适配器**（无状态、无网络、凭据由调用方解析）；目标清单与绑定各自原子落盘、
> **坏文件不覆盖**；出站失败永不阻断会话；完成通知另有**完成闸门**——本轮把活交出去时先不下「已完成」的
> 结论：看两路事实源，`ctx.jobs`（本轮未结算的 job）与 `ctx.agents`（还在跑的 subagent 后代）。
> 下面记的是**为什么这么切**。

## 一、整体结构

```
                     ┌──────────────── Host 半（Node） ────────────────────────┐
  session/event ──▶  │ classify ─▶ goal ─▶ 完成闸门 ─▶ resolveTargets ─▶ 渠道打包 │ ──▶ HTTP 出站
                     │  意图判定   自动轮静默  job + 子代理  目标集合解析   6 种渠道│
                     │                          │  ▲ ▲                            │
                     │                  统一出站 │  │ │ ctx.jobs / ctx.agents（只读）│
                     │                          │  │                              │
                     │                    OutcomeStore(内存)                     │
                     └───────┬────────────────────────────┬──────────────────────┘
                             │ provideService             │ webServer.register(prefix)
                     ┌───────▼────────┐          ┌────────▼─────────┐
                     │ dshNoticeWebhook│          │ Host RPC         │
                     │  (给其他插件)   │          │ /api/dsh-notice- │
                     └────────────────┘          │ webhook/*        │
                                                 └────────┬─────────┘
                     ┌──────────────── 客户端半（浏览器） ───┼─────────┐
                     │ settings.section 注册（order 21）     │         │
                     │ 目标页 / 会话绑定页  ◀── 同源 fetch ───┘         │
                     │ dshNoticeWebhookClient（可嵌入选择器）           │
                     └──────────────────────────────────────────────────┘
```

| 模块 | 职责 | 为什么单独成模块 |
|---|---|---|
| `src/classify.js` | 事件 → 意图（发不发、说什么）；`turn/end` 按**终态**分类（完成 / 中断 / 静默） | 文案与开关判定集中一处，改文案不动链路 |
| `src/goal.js` | goal 自动轮静默、终态去重 | "系统自己唤醒的轮次不该吵人"是独立规则 |
| `src/jobs.js` | **完成闸门**：job 未结算 **或** 本会话还有在跑的 subagent 后代时不推完成，两路都清空后补发 | 读 DSH 的两处事实源（`ctx.jobs` / `ctx.agents`）+ 有时间序状态（pending/宽限计时器），不进主链路 |
| `src/router.js` | 目标集合解析 + 逐目标过滤（按 `eventsMode`）+ 去重 + 冷却 | 判定顺序是语义的一部分，必须单点可读 |
| `src/channels/*` | 每渠道报文与**业务码**判定 | 平台差异只在这层，新增渠道是纯增量 |
| `src/targets.js` / `src/bindings.js` | 两份状态 + 原子写 + 坏文件容忍；关心事件的「全收 / 显式」语义 | 状态是唯一需要跨重启存活的东西 |
| `src/outcomes.js` | 每目标最近 5 条投递结果（内存） | "刚那条为什么没到"要能就地查 |
| `src/rpc.js` | 设置页读写通道（含 revision 栅栏） | 写冲突必须在协议层解决 |
| `src/service.js` | 给其他插件的服务（v2） | 其他插件不该各自监听会话事件 |
| `client.js` | 设置页 + 可嵌入选择器 | 自包含单文件，无打包步骤 |

## 二、十个关键决策

### 1. 绑定是**替代**默认组，不是叠加

会话绑定了目标 → 只发这些目标；绑定为空或全部失效 → 回落默认组。

**为什么**：叠加会让"同一件事发两遍到同一个群"成为默认行为；而用户绑定某个目标的意图恰恰是"改道到这儿"。
失效回落则避免"目标被删后彻底静默"这种更难排查的失败。

### 2. 类型开关是**内容级**，总开关是**通道级**

| 开关 | 作用域 | 命中绑定是否豁免 |
|---|---|---|
| `notifyComplete/Approval/Question` | 内容级（这类一律不发） | **不豁免**——关掉就是不想被这类打扰 |
| `enabled`（总开关） | 通道级（只管默认组） | 豁免——绑定是旁路 |

### 3. 出站失败永不阻断会话，但**必须留下痕迹**

投递是 fire-and-forget；失败只记 warn + 进「最近投递」。HTTP 200 **不等于**送达：
企微/钉钉看 `errcode`、飞书看 `code`，平台回 200 + 业务错误码时按失败处理，并把平台 `errmsg` 带进结果。

### 4. 两份状态都**宁可空表，不可猜**

读文件口径统一为：不存在 → 空表且不建文件；非法 JSON / 未知版本 → 空表且**不覆盖原文件**；单条非法 → 只跳过该条。

**为什么**：绑定丢了的代价远大于少推一条通知；留原文件是给人工抢救的机会。

### 5. 组装点：URL 由 Host 按渠道元数据拼，不由界面拼（REQ-260930215459-d718）

用户只填 key，地址在 Host 侧拼：`composeUrl(target)` 是**唯一**拼装点。这样一来：
前缀与校验规则只有一份（`src/channels/meta.js`），界面与 Host 不会各写一套而分叉；
换平台前缀、加渠道都只改一处。代价是数据模型要多存一个 `key` 字段（见下条）。

### 6. 目标存 key、`url` 是派生值，但**仍要落盘**（REQ-260930215459-d718）

`targets.json` v2 同时写 `key` 与派生出的 `url`——冗余是**故意**的：
旧版本插件只认 `url`，靠它才能回滚后继续投递。旧文件（只有 url）读取时按渠道前缀反解 key，
**反解不出来就保留原地址直投**（记 warn），既不丢目标也不猜。

### 7. 完成通知要问一句「还有活吗」——**两路事实源**，且**抑制必须配兜底补发**
（REQ-261001202058-0fbe 立闸门 · REQ-261005120639-f801 补上子代理这一路）

`turn/end` 只说明"这一轮结束了"，**不等于**"会话完成了"：agent 把活交出去时，本轮照样以 `completed` 收尾。
"活"有两种，而且**必须看两路**——这是本包最容易漏的一处：

| 活 | 事实源 | 关键事实 |
|---|---|---|
| 后台 job（bash / workflow / **one-shot** 子代理） | `ctx.jobs` | 注册了 job，本轮结束 ≠ 活干完 |
| **continuable 子代理**（`subagent` / `subagent_fork`，DSH 默认 preset） | `ctx.agents` | 走 `subagents.startContinuable()`，**不注册 job**——只看 `ctx.jobs` 会漏掉一整类 |

```
turn/end(completed) ──▶ 本会话还有活吗？──有──▶ 压住不推
                            │  ① 本轮未结算的 job（drop: job-running）        └─ 两路都清空 + 宽限内无新轮次 → 补发一次
                            │  ② 在跑的 subagent 后代（drop: subagent-running）
                            │  两者都有（drop: work-running）
                            └──没有──▶ 照常推
```

四条口径（都是踩过或差点踩到的）：

| 口径 | 为什么 |
|---|---|
| job 只算**本轮拉起**的（`startedAt >= 本轮 turn/start`） | 否则一个常驻 job（dev server）会让该会话**永久**收不到完成通知——比误报更糟 |
| 子代理按**活体**算、不按轮次：血统可达 ∧ `origin === 'subagent'` ∧ `status === 'running'`（任意深度） | 子代理的活有界、必然结算，不存在"永久静音"；按轮次过滤还会漏掉"本轮唤醒一个既有子代理"；口径与 DSH 自身的 `runningDescendants` 一致 |
| **抑制 + 兜底补发**，不是只抑制 | DSH 结算后默认会唤醒 agent（`completionDelivery: 'wakeup'`）从而产生新轮次；但 `quiet` 或唤醒预算耗尽时**不开新轮次**，只抑制就等于永远不通知 |
| 拿不准（两路服务都缺 / 无轮次起点 / 判定抛错）→ **照旧发** | 口径是"宁可误报，不可漏报"；降级必须可回归（既有测试文件天然走降级路径） |

**结算信号也是两路**：job 走 `ctx.jobs.events`（settled / removed），子代理走 `ctx.on('subagent/end')`——
但子代理的**存活是"拉"出来的**（每次现查 `ctx.agents.list()`），事件只当"该复检了"的时机，
所以漏一个 epoch 事件也不会让 pending 卡死。

**为什么闸门在 `classify` 之后 `dispatch` 之前**：它只否决"完成"这一类意图，不动授权 / 提问 / goal 终态三条通路；
被否决时**不消耗冷却**（冷却在 dispatch 内部提交）；补发复用**同一条** dispatch，渠道打包、加签、
逐目标过滤、去重、冷却因此自动一致——出站 v1 报文一字未动（补发报文与正常投递**逐字段相等**，e2e 有断言）。

**为什么按形状消费而不是 import DSH 的 jobs / agent 包**：本包零运行期依赖，才能在缺这些服务的组合里照常工作；
形状不符即降级 + 一条 warn（两条路各自独立降级，互不拖累）。

### 8. `turn/end` 的结论由**终态**决定，不由"有没有命中名单"决定（REQ-261001203114-19b6）

判断顺序写死在纯函数 `decideTurnEnd(reason, skipReasons)` 里，顺序即语义：

```
turn/end(reason.kind)
  ├─ aborted                       ──▶ 静默（用户自己按的 Esc）          码: turn-aborted
  ├─ 命中 skipReasons（默认只有 aborted）──▶ 静默                      码: turn-skipped
  ├─ completed                     ──▶ 「会话已完成」                   event: turn/end
  ├─ error                         ──▶ 「会话异常中断（code）」+ 错误事实  event: turn/error
  ├─ interrupted（崩溃孤儿 turn）    ──▶ 「会话异常中断」                 event: turn/error
  ├─ 未知 kind（DSH 未来新增）       ──▶ 「会话异常中断（kind）」          event: turn/error
  └─ blocked / max-tokens / forked ──▶ 静默（**既不推送，也不谎报完成**） 码: turn-not-notifiable
```

| 口径 | 为什么 |
|---|---|
| **只有 `completed` 说「已完成」** | 旧实现是"命中名单就静默，否则当完成"，于是 `error`/`blocked`/`max-tokens`/`forked` 全被说成"跑完了"。报错被说成跑完**比漏报更糟**：用户据此收工 |
| **未知终态按「中断」上报** | DSH 的 `TurnEndReasonMap` 是可合并扩展的（第三方能加终态）。宁可提示"未知终态"，也不默认成"完成" |
| **`blocked` / `max-tokens` / `forked` 不推送** | 它们不代表"干活干到一半停住"（`blocked` 连模型调用都没花），叫了是噪音；但兜底成"完成"是谎报——所以第三条路：静默 + 原因码 |
| **`aborted` 永远静默** | 那是用户自己按的 Esc，自己知道的事不用通知；即使用户把它从 `skipReasons` 移除也仍然静默 |
| **中断不受 goal 自动轮静默影响** | 自动轮被抑制的前提是"系统自己唤醒的轮次不吵人"；而 agent 在无人值守时**报错停下**，恰恰最该叫人 |
| **错误详情单行化 + ≤200 字符，且只进结构化字段** | 正文只留短错误码：换行会破坏各渠道排版，`error.message` 可能含 prompt 片段（日志里只记 code） |
| **出站新增取值 `turn/error` 而不是复用 `turn/end` + 字段** | 接收端可以按 `event` 分流；代价是只认 `turn/end` 的老接收端收不到中断通知——README 已明示 |
| **关心事件加 `eventsMode`（`all` / `explicit`）** | UI 历史上把"全选"物化成显式四项白名单，新增事件后**所有既有目标都会静默过滤掉它**；而"全收"与"我明确只要这些"在旧数据里同形（都可能是四项），必须显式区分 |

### 11. 「谁在说话」只有一处口径：非 direct human 即**注入**（REQ-261002150038-344a）

```
user/message.source.kind
  ├─ 缺失 / 为 'user'（或整条 source 缺失）──▶ direct human ──▶ 本轮算「人的轮次」
  └─ 其余（goal / dive / plugin / 未来新增）──▶ 注入        ──▶ 本轮算「注入轮」
本轮判定：有注入消息且无任何 direct human 消息 ⇒ 注入轮 ⇒ turn/end(completed) 静默
         一轮里一条 user/message 都没有          ⇒ 不静默（不把结构未知当自动）
```

| 口径 | 为什么 |
|---|---|
| **只认 direct human，不再只认 `'goal'`** | 旧实现只把 `dsh-goal-round-driver` 的 `'goal'` 当自动轮；看板 Dive 的自动续跑（`'dive'`）与插件通知（`'plugin'`）被当成人工轮 → **每轮推一条「对话完成」**（用户截图反馈的噪音）。README 早就承诺"系统自己唤醒的轮次不该吵人"，但口径漏了两个来源 |
| **判定收在一个纯函数里（`src/source.js`）** | 静默判定（`GoalTracker`）与「任务」字段取值（`PromptTracker`）以前各写一份 `=== 'goal'`，漏一处就出噪音；现在两处共用同一函数，`grep` 可验 |
| **未知 / 形状异常的 kind 一律算注入** | 新增 kind 默认**安静**而不是默认吵闹；判定不抛错、不影响中断推送 |
| **人插话优先** | 本轮只要出现过 direct human 消息就不再静默——"人在旁边说话却不响"比多响一次糟 |
| **静默只挡「完成」** | 注入轮里 agent 报错/崩溃**照推**中断（沿用决策 8 的同一分支） |
| **注入正文不进「任务」字段** | 否则卡片上会出现「任务：继续执行需求 REQ-…（第 35 回合）」这种把系统提示冒充成用户要求的假信息 |
| **飞书卡片不再重复「类型」行** | 卡片标题栏已给出事件（`✅ 对话完成` 等），正文再列一行是纯重复；纯文本渠道没有标题栏，**保留**该行（`DEFAULT_FIELDS` 不动） |
| **设置页预览同步过滤** | 预览与真卡片必须是同一口径，否则"预览有、真卡片没有"= 预览说谎（卡片区过滤，纯文本区保留） |

### 9. 文案配置**只落在目标上**，不做全局（REQ-260930215459-d718）

每个渠道能力不同：飞书能发交互式卡片与 `<text_tag>` 标签、企微/钉钉是 markdown、
Slack/Discord 又是 Block Kit/Embeds。**一套全局配置不可能同时对五种渠道正确**，
所以文案（要哪几行、摘要长度、时间格式、链接、模板）存在**目标记录**里；
插件配置里的 `payload` 只作为**出厂默认**兜底。投递时按两级取值：`目标自己的 ?? 插件默认`。

### 10. 「问用户」要旁听 `ctx` 的 waterfall，不是会话事件（REQ-260930215459-d718）

DSH 里所有提问（内建工具、权限流、**二次开发插件的弹框**）都走
`ctx.waterfall(scopeTarget(agent, agent), 'user-questions/request', …)` ——
这是 **ctx 事件，不在 `session/event` 流里**。只订阅会话事件的插件**根本收不到插件弹框**。
正确姿势：在根 ctx 上 `ctx.on('user-questions/request', (request, next) => { …通知…; return next() })`，
**必须 `next()` 放行**（吞掉提问会导致弹框不弹），且通知失败要兜住、绝不能影响提问。

## 三、契约与边界（跨需求稳定）

| 契约 | 版本 | 兼容策略 |
|---|---|---|
| 出站「通用自定义」报文 | v1 | 新增字段/事件取值是追加式，版本不动；`turn/error` 是新增取值，只有它带 `reason` / `error` 两个字段 |
| Host Service `dshNoticeWebhook` | v2 | v1 四方法一个不删；消费方应放宽为 `>= 1` |
| 客户端服务 `dshNoticeWebhookClient` | v1 | 每次返回新元素；插件卸载后返回 `null` |
| `targets.json` | **v3** | 目标存 `key` + 派生 `url`；`eventsMode` 是**单条记录上的新增可选字段**，旧版本忽略（回滚不丢目标）。v1 文件按前缀反解升级，反解失败原样直投 |
| `bindings.json` | v1 | 新段（`targetBindings`）是**新增顶层键**，旧版本忽略即可，回滚不丢数据 |

## 四、踩过的坑（值得记的教训）

| 坑 | 现象 | 教训 |
|---|---|---|
| `Config` 没从**插件入口**导出 | 单元测试全绿，但 Loader 读不到 schema（`Config.listConfigs` 无此项） | 插件契约要在**真实装载路径**上验（本仓做法：走 profile 链接加载一次） |
| 测试用了默认状态路径 | 跑一次测试就在用户 `$DSH_HOME` 里积了 25 条残留目标 | 测试**一律**显式传临时路径；`tempHome()` 不改进程环境变量等于没隔离 |
| 对异步写入的结果直接断言 | 全量并发偶发 `4 !== 5`（42ms 内失败 → 不是超时） | 断言前先等**要断言的那份**数据；等待器超时要抛带条数的错，别静默返回计数 |
| 弹框"选项或自定义输入"二选一 | 依赖"既选又填"的校验路径必然走不通 | 边界层给显式兜底文案（台账能看出"未附实际结果"），别让它变成整条路径不可用 |
| 原型只在设计文档里、没逐元素落到代码 | 交付后用户一眼看出「没按原始实施」 | 原型里的每条元素（分组/徽标/id/按钮层级）都要有**可断言的落点**——本轮把 12 项差距写进 frontend.md 并逐条加测试断言 |
| 给"显式白名单"加分支时漏了 `goal/*` 通配 | 新分支只看 `events.includes(event)`，于是「勾了目标终态」的目标突然收不到 goal 事件——**既有用例当场抓住** | 过滤规则只能有**一份**实现（`listedEventMatches`）；新分支要复用旧分支的全部语义，而不是"看起来等价"地重写 |
| UI 把「全选」物化成显式列表 | 新增事件类型后，老目标的白名单里没有它 → 通知被静默过滤，用户毫不知情（比漏发更难发现） | "全收"必须是**数据上的一个状态**（`eventsMode: 'all'` + 空列表），不能靠"当前所有事件都勾上了"来近似 |
| 静默名单排在特例之前 | `aborted` 默认就在 `skipReasons` 里，于是专门为它写的 `turn-aborted` 原因码**永远不可达** | 判定顺序是语义的一部分：把"更具体的原因"排在"更宽泛的名单"之前，否则码形同虚设 |
| 事件载荷形状靠猜 | 「任务」整行在通知里消失 | DSH 的 `user/message` 载荷**就是消息本身**（`data.content`），我却按 `data.message.content` 取值 → 取空。**收到真实通知后回看才发现**；已加真实形状的回归用例 |
| 拿错通道去「拦截」 | 插件弹框完全没有通知 | 提问走 **ctx waterfall**，我订阅的是 `session/event` —— 通道不对，怎么改判定都收不到 |
| 端到端用例里断言排在关服务之后 | 断言失败时进程挂死（CI 表现为超时） | 所有起 HTTP 服务的用例一律**先关服务再断言** |
