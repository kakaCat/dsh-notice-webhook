# 项目说明书

> **TL;DR**：本包是 DSH 的通知插件——**该被叫一声的时候才叫**。这份说明书讲三件事：
> 这个包一路长成了什么样（演进叙事）、今天能做什么（能力清单）、哪些取舍不许再翻案（累积约束）。
> 单点的架构细节在[架构与关键决策](notification-plugin.md)，排障在[运维与排障](../guides/operations.md)。

## 二、今天能做什么（能力清单）

| 能力 | 人话 |
|---|---|
| 三类事件推送 | 对话完成 / 需要你允许操作 / 需要你回答一个问题 |
| 六种渠道 | 企业微信、飞书、钉钉、Slack、Discord、通用自定义（原样 JSON） |
| 多目标与绑定 | 一条通知可同时进多个群；某个会话可改道到专属目标（绑定**替代**默认组） |
| 界面配置 | 设置 → 通知：增删改目标、勾关心的事件、看最近投递结果；不用重启 Host |
| 完成闸门 | 本轮把活交出去了（后台 job **或**在跑的子代理）就**不报「完成」**；等活干完再补一条真的完成通知 |
| 自动跑不吵人 | 系统自己唤醒的轮次（goal 自动轮 / 看板 Dive 续跑 / 插件注入）**不推「对话完成」**；你在这一轮插过话、或这轮报错停下，才响 |
| 可回滚 | 老配置原样能跑；`jobAwareComplete: false` 一键关掉整个完成闸门（热改）；卸载零残留 |
| 给其他插件用 | Host Service v2（`bind/bindTargets/unbind/resolve/resolveAll`）+ 客户端选择器 v1 |

### 通知长什么样（REQ-260930215459-d718 之后）

一条通知不是「一行文案」，而是**带上下文的报文**：

| 行 | 内容 | 来自 |
|---|---|---|
| 类型 | ✅ 对话完成 / ❓ 等待回答 / 🔐 等待授权 / 🎯 目标完成 / ⛔ 阻塞或轮次耗尽（**飞书卡片这一行只在标题栏出现，正文不再重复**） | 事件判定 |
| 会话 | 会话名 + `#短id`（飞书渲染成彩色标签） | 会话对象实时标题优先，`session/title` 事件兜底 |
| 工作区 | 目录名（默认）或全路径 | `session.header.cwd` |
| 任务 | 本轮最后一条**人工** `user/message` 的摘要 | 摘要跟踪器（**只认 direct human**：goal / Dive / 插件注入都不计入） |
| 详情 | 问的是（问题正文）/ 工具 / 目标状态+轮次 | 事件载荷 |
| 时间 | 默认 `YYYY-MM-DD HH:mm` | 投递时刻 |
| 链接 | `dsh://open`（飞书只在 http(s) 时才做成按钮） | `payload.linkUrl` |

**文案按目标配**（不是全局）：各渠道能力不同，飞书是卡片+标签、企微/钉钉是 markdown、
Slack/Discord 是另一套；一套全局配置不可能都对。目标里 `payload: null` = 用插件配置的默认。

### 「问用户」的两个来源（最容易漏的一处）

| 来源 | 通道 | 怎么被通知 |
|---|---|---|
| 内建 `ask_user_question` 工具 | 会话事件 `tool/call` | 会话事件订阅 |
| **权限流 / 二次开发插件的弹框**（如 pmboard 确认框） | **`ctx` waterfall `user-questions/request`** | **根 ctx 旁听该 waterfall，且必须 `next()` 放行** |

只订阅 `session/event` 会**完全看不到插件弹框**——这是本包最容易踩的通道错位。

## 三、完成闸门（本包最容易误解的一处）

**为什么需要**：`turn/end` 只说明"这一轮结束了"。agent 把活交出去时本轮照样以 `completed` 收尾——
过去插件据此推「会话已完成」，使用者回来发现活还在跑。这是**误报「已停止」**，也让「完成」这个信号贬值。

**活有两种，闸门要看两路**：

| 活 | 事实源 | 为什么必须看它 |
|---|---|---|
| 后台 job（bash / workflow / **one-shot** 子代理） | `ctx.jobs` | 它们会注册 job，本轮结束 ≠ 活干完 |
| **continuable 子代理**（`subagent` / `subagent_fork`，DSH 默认 preset 的形态） | `ctx.agents` | 它们走 `subagents.startContinuable()`，**不注册任何 job**——只看 `ctx.jobs` 会漏掉这一整类（2026-10-05 修的就是它） |

**今天的行为**：

```
本轮结束 ──▶ 本会话还有活吗？ ──有──▶ 不推（日志 drop: job-running / subagent-running / work-running）
                  │  ① 本轮拉起、未结算的 job                 └─ 两路都清空 + 1.5s 内无新轮次 → 补发一条
                  │  ② 在跑的 subagent 后代
                  └─没有──▶ 照常推
```

**四条不许翻案的口径**（详见[架构决策 7](notification-plugin.md)与需求文档）：

1. **job 只算本轮拉起**的——否则常驻 job（dev server）会让该会话永久静音；
2. **子代理按活体算，不按轮次**——血统可达 ∧ `origin === 'subagent'` ∧ `status === 'running'`（任意深度）；
   子代理的活有界、必然结算，不会像常驻 job 那样永久静音；口径与 DSH 自身的 `runningDescendants` 一致；
3. **抑制必须配兜底补发**——DSH 的结算唤醒不是强保证（`completionDelivery: 'quiet'` 或唤醒预算耗尽时不开新轮次）；
4. **拿不准一律照发**——两路服务都缺失、没有轮次起点、判定抛错，全都退回旧行为（宁可误报，不可漏报）。

**怎么关**：配置 `jobAwareComplete: false`（volatile，改完即时生效，不用重启 Host）——它是**整个完成闸门**的开关，
同时管住 job 与子代理两路。

## 四、累积约束（跨需求稳定，改动前先看这里）

- 出站 v1 报文契约不得破坏（新增字段/事件取值是追加式）；补发也必须走同一条出站通路；
- 判定顺序是语义的一部分：`classify → goal → 完成闸门 → dispatch`，静默轮在闸门**之前**返回；
- 两份状态文件宁可空表不可猜：坏文件不覆盖、单条非法只跳过；
- 失败隔离：任何外部调用异常都不得让会话报错，也不得让其他目标不投递；
- 零第三方运行时依赖；不 import DSH 内部包（按**形状**消费 `ctx.jobs` / `ctx.agents` / `subagent/end` 事件，
  才能在缺这些服务的组合里照常工作）；
- 凭据只引用不明文：界面与日志都不回显密钥。
