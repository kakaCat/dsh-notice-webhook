## UC-1 离开电脑也不错过阻塞点 `serves: FR-1, FR-2, FR-3`

- **用例角色**：让 Agent 跑一个长重构、人去做别的事的使用者。
- **前置条件**：插件已装载并配置 `webhookUrl`；接收端能收 HTTP。
- **交互流程**：
  1. Agent 执行到需要授权的命令，DSH 弹授权框（人不在）；
  2. 插件把「需要你允许执行操作（Bash）」POST 到 webhook；
  3. 接收端转成手机提醒；
  4. 人回到电脑点「允许」，任务继续；
  5. 一轮跑完，插件再推「标题 · 会话已完成」。
- **异常流**：
  - 接收端挂了 → 步骤 2/5 只在 Host 日志留 warn，**会话本身照常阻塞在授权框**（不会因为通知失败而放行或终止）；
  - 手机提醒延迟到达 → 人回到电脑时 DSH 界面里的授权框仍在原地等待，信息不丢。
- **后置条件**：会话状态与"没有装插件"时**完全一致**；差别只在于人知道得更早。
- **完成标志**：人能在不盯着浏览器的情况下，于 1 分钟内得知"有东西在等我"。

## UC-2 其他插件把会话绑到自己的通道 `serves: FR-6, FR-8`

- **用例角色**：看板 / IM 类插件的作者，希望"这个项目的会话提醒进这个群"。
- **前置条件**：两个插件同装在一个 Host；消费方在自己的 `apply` 里 `inject` 服务。
- **交互流程**：
  1. 消费方校验 `ctx.dshNoticeWebhook.version === 1`；
  2. 调用 `bind(sessionId, 'https://example.com/project-hook')`；
  3. 该会话此后的三类提醒改走项目群；
  4. 会话结束或项目收尾时，消费方调 `unbind(sessionId)`，回落默认地址。
- **异常流**：
  - 本插件未安装 → `ctx.dshNoticeWebhook` 为 `undefined`，消费方**静默降级**（自身功能不受影响）；
  - `bind` 传了非法地址 → 返回 `false`，消费方按返回值决定是否重试/告警；
  - 使用者把本插件卸载 → 服务消失，绑定随之失效，消费方下次调用拿到 `undefined` 并降级。
- **后置条件**：**只有**该会话的推送改道，其他会话仍走默认地址；总开关对已绑定会话不生效（见 FR-7）。
- **完成标志**：项目群只收到该项目会话的提醒；公共群收不到该项目会话的提醒。

## UC-3 goal 自动跑轮全程安静、卡住时叫人 `serves: FR-11`

- **用例角色**：用看板 dive 模式挂一个需要跑几十轮的需求的使用者。
- **前置条件**：DSH 已装载 `dsh-goal` + `dsh-goal-round-driver` + 本插件；该会话已创建 goal。
- **交互流程**：
  1. goal 进入 `active`，driver 自动注入轮次（`source.kind = 'goal'`）；
  2. 第 1…N 轮依次结束 → 插件识别为自动轮，**一条都不发**；
  3. goal 跑到 `complete` → 插件推「标题 · 目标已完成」；
  4. 或者轮次耗尽 → driver 以 `code = 'round-limit'` 置 `blocked` → 插件推「标题 · 目标轮次耗尽（N/N）」。
- **异常流**：
  - 人在自动轮之间插话（`/steer`）→ 该轮含人工输入，**照常推送**（人是坐在电脑前的，不该被静默）；
  - goal 被 `paused` 或清除 → **不推**（人的主动操作，不需要被通知）；
  - 插件在 goal 已经 `blocked` 之后才加载 → 该终态**不补发**（已知局限，见 architecture.md 遗留问题）。
- **后置条件**：接收端在整段自动跑轮期间保持安静，只在终态收到 1 条。
- **完成标志**：一个跑 20 轮的 goal，接收端总消息数 ≤ 2（1 条终态 + 可选 1 条人工轮）。
