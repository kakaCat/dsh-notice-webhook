# 架构设计（REQ-260930155231-0862）

> 本份讲"怎么搭"。接口签名与报文契约见 [interfaces.md](interfaces.md)；数据结构见 [data-model.md](data-model.md)；测试见 [test-cases.md](test-cases.md)。

## TL;DR `serves: FR-1, FR-2, FR-3`

- **形态变化**：从 **Host-only** 变成 **Host + Client 双半**（客户端半手写 lazy factory，**不需要打包器**）。
- **新增三层**：渠道适配层（每个 app 一个纯函数模块）、目标清单层（自有文件 + CRUD）、多目标路由层（扇出 + 逐目标过滤）。
- **不动的三层**：事件分类（`src/classify.js`）、goal 层（`src/goal.js`）、投递内核（`src/deliver.js`）——只改它们的**调用点**，不改职责。

## 目标与总体方案 `serves: FR-1, FR-2, FR-3, FR-5`

**问题**：现有实现是"一条默认地址 + 一个窗口一条地址 + 原样 JSON"。要发到不同 app 就得自己写适配层；要发多个地方就得自己搭转发服务；换地址得改 YAML。

**设计方案**：把"地址"抽象成**目标**（渠道 + 地址 + 凭据 + 开关 + 事件过滤），把"发一条"变成"发到一组目标"。

三个新部件各管一件事：

| 部件 | 职责 | 为什么单独成层 |
|---|---|---|
| 渠道适配层 | 把通知 + 目标 → 该渠道的 `{url, headers, body}`；并判定业务成功 | 每个 app 的报文与错误码都不同，必须隔离，且要能离线单测 |
| 目标清单层 | 目标记录的持久化与 CRUD（界面 / RPC / Service 共用一份） | 唯一事实源；界面与插件调用方不能各存一份 |
| 多目标路由层 | 会话 → 目标集合 → 逐目标过滤 → 去重 | 总开关/类开关/目标过滤的**叠加顺序**必须只有一处 |

**不这么做的后果**：报文拼装散落在路由里，加一个渠道要改三处；目标清单两处存储会出现"界面删了、Service 还看得见"；过滤顺序散落会导致"关掉类开关却仍被某目标收到"这类口径分叉。

## 关键流程 `serves: FR-3, FR-4, FR-5, FR-6`

### 从事件到投递 `serves: FR-3, FR-4, FR-5, FR-6`

```
session/event
      │
      ▼
 classify ──▶ 意图 { kind, event, message } 或 null
      │                                   │
      │                          kind 是 complete 且 goal 自动轮？──是──▶ 丢弃
      ▼
 ┌──────────────────────────────────────────────┐
 │ 1. 类开关（内容级，最先）                     │  notifyComplete/Approval/Question 关闭 → 整体丢弃
 └───────────────┬──────────────────────────────┘
                 ▼
 ┌──────────────────────────────────────────────┐
 │ 2. 解析目标集合                               │
 │    窗口绑定 targetBindings[sid] 非空？        │
 │      是 → 取这些目标（存在且 enabled）        │
 │      否 → 默认组（isDefault && enabled）      │
 └───────────────┬──────────────────────────────┘
                 ▼
 ┌──────────────────────────────────────────────┐
 │ 3. 总开关（只管默认组）                       │  仅当走的是默认组时看 enabled
 └───────────────┬──────────────────────────────┘
                 ▼
 ┌──────────────────────────────────────────────┐
 │ 4. 逐目标事件过滤（FR-4）                     │  events 为空 = 全收
 └───────────────┬──────────────────────────────┘
                 ▼
 ┌──────────────────────────────────────────────┐
 │ 5. 去重（同渠道 + 同地址只发一次）             │
 └───────────────┬──────────────────────────────┘
                 ▼
        逐目标：buildRequest → deliver → 记结果（互不影响）
```

**绑定是替代不是叠加**：命中窗口绑定后**不再**追加默认组——否则同一条通知会发两遍到同一个群（第 5 步的去重只按 `channel+url`，跨"绑定组 ∪ 默认组"的语义噪声仍会留在那里）。

### 为什么过滤顺序是这个顺序 `serves: FR-4, FR-6`

| 顺序 | 这一层 | 越界的后果 |
|---|---|---|
| 1 类开关 | 内容级：这类事件根本不该发 | 放到后面，会出现"某目标收到本该静音的事件" |
| 2 目标解析 | 先知道有哪些目标 | 先算总开关就无法区分"默认组"与"窗口绑定" |
| 3 总开关 | 只作用于默认组 | 放到 2 前面，窗口绑定会被一起关掉（违反 FR-6 既有语义） |
| 4 目标过滤 | 每个目标自己的偏好 | 放到打包之后等于白打包 |
| 5 去重 | 按渠道 + 地址 | 不去重会把同一条消息推两遍给同一个群 |

### 渠道适配的两段式 `serves: FR-1`

每个渠道模块导出两个纯函数，**没有状态、没有网络**：

```
buildRequest(target, payload, now) ──▶ { url, headers, body } | { error }
isSuccess(status, parsedBody)      ──▶ { ok, reason? }
```

- `buildRequest` 负责：报文形状、加签（钉钉/飞书）、自定义头的合并；
- `isSuccess` 负责：HTTP 状态码 + **业务错误码**（企微/飞书/钉钉 200 也可能带 `errcode != 0`）；
- 投递内核（既有 `deliver.js`）只负责网络、超时、重试、脱敏日志——它不知道"渠道"是什么。

**为什么这样切**：渠道的报文与错误码是最容易写错、也最值得单测的部分；把它做成纯函数即可在没有网络的情况下把六个渠道全测一遍。

## 错误处理 `serves: FR-1, FR-3, FR-7, FR-8`

| 错误码 / 情况 | 触发条件 | 使用者看到什么 | 如何恢复 |
|---|---|---|---|
| `channel/unknown` | 目标写了不认识的渠道 | 保存时即被拒；已存在的坏数据在投递时记 warn 并跳过该目标 | 改回已知渠道 |
| `channel/build-failed` | 加签缺 secret、地址缺必要路径 | 该目标投递失败，原因记入结果 | 补凭据 / 改地址 |
| `deliver/business-code` | HTTP 2xx 但 `errcode != 0` / `code != 0` | 该目标标记失败并带上业务错误信息 | 按 app 提示处理（如钉钉关键词） |
| `targets/persist-failed` | 数据文件不可写 | 保存被拒（**不谎报成功**）+ warn | 修权限 |
| `targets/corrupt` | 文件非法 JSON / 未知主版本 | 按空清单启动 + warn，**不覆盖原文件** | 人工修复或删除 |
| `rpc/unavailable` | 客户端半在、Host RPC 不可达 | 设置页显示错误态，不静默变空列表 | 刷新 / 检查 Host |

**总原则**：单目标失败绝不影响其他目标（FR-3）；任何失败都不得让会话报错。

## 安全与性能 `serves: FR-7`

**安全风险**：

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 加签密钥出现在界面/日志/服务返回值 | 凭据泄漏 | 只存 `secretRef`；界面与服务只回"是否已配置"；日志沿用既有脱敏（只记 host） |
| 自写设置页越权读写 | 其他插件/用户配置被改 | RPC 走 Host 既有认证与信任域（与 dsh-im 同口径），只读写本插件自己的数据 |
| 目标地址被填成内网/文件协议 | SSRF / 越权 | 地址必须 http(s)（沿用既有校验）；不做服务端跳转跟随 |
| 客户端半注入 DOM / 抢样式 | 破坏宿主界面 | 只注册一个 `settings.section`；样式用主题 token；不替换根节点 |

**性能影响**：

| 指标 | 改前 | 改后 | 可接受吗 |
|---|---|---|---|
| 单次事件处理 | 1 次路由判定 | 目标数 × 纯函数打包（无网络等待，异步投递） | 是（目标数是个位数） |
| 内存 | 标题 + goal 状态 | 加"目标清单 + 最近结果（每目标 5 条）" | 是 |
| 设置页数据量 | — | 目标数十条量级 | 是 |
