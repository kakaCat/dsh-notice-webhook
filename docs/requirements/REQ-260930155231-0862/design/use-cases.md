## UC-1 授权与完成分流到不同群 `serves: FR-4, FR-5`

- **用例角色**：团队使用者，有"值守群"与"项目群"。
- **前置条件**：已装插件并可打开设置页。
- **交互流程**：
  1. 新增目标「值守群-钉钉」，事件勾选**授权**；
  2. 新增目标「项目群-企微」，事件勾选**完成**；
  3. 两个目标都设为默认组成员；
  4. 跑任务：出现授权请求 → 值守群收到；一轮结束 → 项目群收到。
- **异常流**：
  - 钉钉目标因未配关键词被平台拒（HTTP 200 + `errcode`）→ 结果里显示平台原因，**企微目标照常收到**；
  - 某一目标的地址写错 → 只有它失败，另一个不受影响。
- **后置条件**：两类事件各自只进该进的群。
- **完成标志**：值守群**没有**收到完成类消息，项目群**没有**收到授权类消息。

## UC-2 临时加一条通道，不用重启 `serves: FR-2, FR-8`

- **用例角色**：单人使用者，正在跑长任务。
- **交互流程**：
  1. 打开设置页 → 新增目标（选 Slack，粘地址）→ 保存；
  2. 点「发送测试」→ 手机上收到测试消息；
  3. 不重启 Host，等下一次通知 → 新通道也收到。
- **异常流**：
  - 地址非法（`ftp://…`）→ 保存被拒并提示，列表不变；
  - 两个页面同时编辑 → 后保存的那个拿到"版本过期"，页面自动刷新到最新，不会静默覆盖。
- **后置条件**：目标清单持久化；重启后仍在。
- **完成标志**：从"打开设置页"到"测试消息到达"不超过 1 分钟，且**全程没有重启 Host**。

## UC-3 其他插件把项目会话绑到项目群 `serves: FR-3, FR-5`

- **用例角色**：看板 / IM 类插件作者；**以及**使用该插件的团队使用者（他要在弹框里勾）。
- **前置条件**：本插件已装且设置了至少一个目标。
- **交互流程**：
  1. 消费方 `inject: ['dshNoticeWebhookClient']`，校验 `version === 1`（拿不到就**不显示绑定入口**）；
  2. 使用者在看板里点「绑定会话到 Webhook」→ **看板自己的弹框**打开；
  3. 弹框里挂的是**我们的选择器** `renderTargetPicker({ sessionId, selected, onConfirm })`——目标列表、默认组标记、空态引导都由我们渲染；
  4. 使用者勾选目标 → 点确定 → `onConfirm(ids)`；
  5. 看板调 Host Service `bindTargets(sessionId, ids)` → 该项目会话的提醒只进这些目标。
- **异常流**：
  - 目前一个目标都没有 → 选择器显示引导「还没有 webhook 目标，先去设置里加一个」，而不是空白框；
  - 使用者在弹框里一个都不选就确定 → `onConfirm([])` → 解绑全部，回落默认组；
  - 绑定写入失败（目标 id 不存在）→ `bindTargets` 返回 `false`，**整笔不生效**（不做部分绑定），看板按自己的方式提示；
  - 消费方是旧版本（写死等 `version === 1` 之外的判断）→ 隐藏入口即可，旧 `bind`/`resolve` 仍可用；
  - 目标在别处被删除 → 引用它的绑定失效（视为未绑定），不报错，回落默认组。
- **后置条件**：只有该项目会话改道；其他会话仍走默认组。
- **完成标志**：项目群收到该项目会话的提醒；公共群收不到。

## UC-4 老用户升级零改动 `serves: FR-9`

- **用例角色**：已经在用上一版插件的使用者。
- **前置条件**：profile 里只有 `webhookUrl`；`bindings.json` 是老的 `sessionId → url` 形态。
- **交互流程**：
  1. 升级插件（不碰任何配置）；
  2. 跑一轮任务。
- **异常流**：
  - 想回滚：卸载新版 → **老绑定仍生效**（新版一直在维护 `bindings` 段）；
  - `targets.json` 存在但为坏文件 → 空清单 + 告警，**不覆盖**，且 legacy 通道仍工作。
- **后置条件**：行为与升级前一致；不会出现"升级后一条通知都收不到"。
- **完成标志**：升级前后收到的报文字段完全一致（`version` 仍为 `1`）。

## UC-5 按会话查绑定并解绑 `serves: FR-5, FR-6`

- **用例角色**：使用者（或帮忙排查的人）。
- **触发**：某个会话的提醒发去了不该去的地方，或他不想再让某会话占用专属通道。
- **前置条件**：至少存在一条会话绑定（通常由看板等宿主经选择器建立）。
- **交互流程**：
  1. 打开 设置 → Webhook 通知 → **会话绑定** 标签；
  2. 列表按会话列出：会话标题 + id 尾串、绑定的 webhook（chips）、操作；
  3. 找到目标会话 → 点「解绑」→ 二次确认「解绑后该会话改为发默认组，确认？」；
  4. 确认 → 该行消失，会话**立刻回落默认组**；下一次通知按默认组投递。
- **异常流**：
  - 解绑时页面版本过期 → `409` → 提示"已被其他页面修改，已刷新"，用户看到最新绑定再决定；
  - 该会话的绑定里含**已被删除的目标** → 行内显示「⚠ 目标已删除（回落默认组）」并提供「清理」，不显示成正常绑定；
  - 两个页面同时解绑 → 后者收到 `404`（绑定已不存在）→ 刷新列表即可，不报错。
- **后置条件**：绑定被清空；若该会话本就没有其他绑定，它回到默认组。
- **完成标志**：会话绑定页不再出现该会话；该会话的下一次通知落到默认组的目标。
