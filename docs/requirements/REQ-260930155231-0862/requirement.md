# 需求说明（REQ-260930155231-0862）

> 面向：产品、开发、测试、使用者——**写给人看，不是写给代码看**。

## TL;DR

- **这是什么**：给已有的 DSH Webhook 通知插件补上"多渠道 + 多目标 + 界面配置"。
- **为什么现在做**：现在只能填一条裸地址、且必须手改 `cordis.patch.yml`；而实际要发的地方是**不同 app**（企业微信/飞书/钉钉/Slack/Discord），每个 app 的报文格式都不一样。
- **做完得到什么**：在界面里加几个目标、选渠道、填地址，通知就能同时发到多个 app；某个 app 挂了不影响其他。

```
                       ▼

                       │

```

## 产品定义

**多渠道路由的 Webhook 通知**：在已有通知插件之上，把"一条固定地址"升级为"一份可管理的目标清单"。

每个目标是一个**具体的落点**：选一个渠道（决定报文长什么样）、填该渠道的地址与密钥、决定它关心哪类事件。

**核心价值**：把"改配置文件才能换地址、换个 app 就要重写报文"变成"界面里加一条目标，各 app 各收各的、互不牵连"。

**与现状的区别**：

- 现有插件：一条默认地址 + 原样 JSON；换 app 得自己写适配层（或换插件）。
- 参考项目 [dsh-im](https://github.com/xmanrui/dsh-im)：走**机器人凭据 + 长连接**，能力强但接入重（扫码/建应用/权限审批）。
- 本需求：走**入站 webhook**（很多 app 都提供"给你一条 URL"的群机器人），接入成本是一条地址；不追求双向、不追求富交互。

## 用户与角色

| 角色 | 什么场景用 | 痛点 |
|---|---|---|
| 单人开发者 | 完成/授权/提问想同时进企业微信和手机推送 | 现在只能填一条地址，想多发几处得自己搭转发服务 |
| 团队（多群分流） | 授权提醒进"值守群"，完成提醒进"项目群" | 现在所有事件走同一条地址，无法按事件分类 |
| 其他 DSH 插件作者 | 把自己管的会话绑到项目专属目标 | 现在只能绑一条地址，且要自己拼该平台的报文格式 |

### 功能点清单

- **FR-1: 按渠道打包报文**（P0）—— 企业微信机器人 / 飞书自定义机器人 / 钉钉机器人 / Slack / Discord / 通用自定义，六种渠道各有自己的请求体形状
- **FR-2: 界面管理目标清单**（P0）—— 在 DSH 界面里新增 / 修改 / 删除 / 启停目标，不用手改配置文件
- **FR-3: 多目标扇出**（P0）—— 一条通知按解析出的目标集合逐个投递，**单个目标失败不影响其他目标**

- **FR-7: 凭据不回显**（P0）—— 钉钉加签 secret、飞书签名 secret 等以凭据引用方式保存，界面上只显示"已配置/未配置"
- **FR-8: 配置改完即时生效**（P0）—— 保存后不需要重启 Host，下一次通知即按新目标投递
- **FR-9: 兼容既有交付**（P0）—— 老配置（默认地址 + 原样 JSON + 老窗口绑定）不改一行也能继续工作

**优先级说明**：P0 = 缺了核心价值不成立；P1 = 本期尽量交付。

### 功能点详细说明

### 功能点 FR-1：按渠道打包报文

**功能描述**：每个目标选定一个渠道，插件负责把通知转成**该渠道认识**的请求体。

**详细说明**：

- **使用场景**：企业微信群机器人只认 `msgtype` 结构；Slack 只认 `text` 字段。投错格式 = HTTP 200 但消息不出现。
- **操作流程**：目标解析出渠道 → 调用该渠道的打包函数 → 与地址、密钥一起交给投递层。
- **预期结果**：六种渠道的请求体形状固定（见「接口契约」），且**判定成功不只看 HTTP 状态码**。
- **边界条件**：
  - 企业微信 / 飞书 / 钉钉在 HTTP 200 时仍可能在 body 里返回业务错误码（如钉钉 `errcode != 0`）→ 必须判定为**失败**并记录原因；
  - 通用自定义渠道保持现有契约不变（原样 JSON），不做任何加工。

**验收标准**：

1. 对六种渠道各发一条，接收端收到的请求体形状与「接口契约」表逐字段一致。
2. 钉钉端点返回 HTTP 200 + `{"errcode":310000,"errmsg":"keywords not in content"}` → 插件判定为**失败**，并在结果里带上该 errmsg。

---

### 功能点 FR-2：界面管理目标清单

**功能描述**：在 DSH 界面里完成目标的新增、修改、删除与启停。

**详细说明**：

- **使用场景**：换群、加一个渠道、临时停掉某个目标，都不该去编辑 YAML。
- **操作流程**：
  1. 打开插件的配置入口；
  2. 新增目标：选渠道 → 填地址 → 按需填密钥；
  3. 保存。
- **预期结果**：
  - 目标列表能增删改，字段校验失败时当场提示且**不落盘**；
  - 保存后的目标出现在列表里，且通知按新清单投递。
- **边界条件**：
  - 地址非法（非 http/https、或缺少该渠道必需路径）→ 拒绝保存并提示；
  - 渠道必填项缺失（如钉钉开启了加签却没给 secret）→ 拒绝保存。

**验收标准**：

1. 在界面上新增一个"企业微信机器人"目标并保存 → 目标列表出现该条，且下一次通知发到该地址。
2. 填入 `ftp://x` 保存 → 被拒绝且列表不变。

### 功能点 FR-3：多目标扇出

**功能描述**：一条通知发到多个目标时，逐个投递且互不影响。

**详细说明**：

- **使用场景**：完成事件既进项目群又进个人手机。
- **操作流程**：解析出目标集合 → 依序（或并发）逐目标打包投递 → 汇总结果。
- **预期结果**：
  - 3 个目标里 1 个不可达 → 另外 2 个照常收到；
  - 失败目标的失败原因被单独记录，不污染其他目标的结果。
- **边界条件**：
  - 目标集合为空 → 不投递，记一条 debug（等同现状的"无目标"）；
  - 同一地址在清单里重复出现 → 按目标去重，避免重复推两条。

**验收标准**：

1. 配置两个目标（一个正常、一个指向 `127.0.0.1:1`）→ 正常目标收到 1 条，失败目标记录失败，进程无未捕获异常。
2. 同一个地址配成两个目标并都启用 → 该地址只收到 1 条。

---

### 功能点 FR-4：逐目标事件过滤

**功能描述**：每个目标可以只关心某几类事件。

**详细说明**：

- **使用场景**：授权提醒只进值守群，完成提醒只进项目群。
- **操作流程**：目标上勾选关心的事件类型（`turn/end`、`approval/asked`、`ask_user_question`、`goal/*`）。
- **预期结果**：
  - 目标 A 只勾"授权" → 完成事件不到 A；
  - 未勾任何类型 → 视为"全收"（默认），不是"都不收"。
- **边界条件**：
  - 类型开关（`notifyComplete` 等）与目标级过滤是**两层**：类型开关关闭时该类一律不发（含所有目标）；目标级过滤再按目标筛。
  - goal 终态事件属于"goal/*"类，独立于三类通知开关（沿用既有语义）。

**验收标准**：

1. 目标 A 只勾 `approval/asked` → 触发完成事件，A 收不到；触发授权事件，A 收到。
2. 目标 B 不勾任何类型 → 三类事件都收到。

---

### 功能点 FR-5：会话窗口绑定多个目标

**功能描述**：一个会话窗口可以绑定若干目标；未绑定的会话走默认目标组。

**详细说明**：

- **使用场景**：某个客户项目的会话只发到该项目群，不进公共群。
- **操作流程**：通过界面或 Host Service 把 `sessionId` 与若干目标 id 关联；解绑则回落默认组。
- **预期结果**：
  - 绑定 A+B 的窗口 → 事件同时到 A 与 B；
  - 未绑定的窗口 → 走默认组；
  - 解绑后立刻回落默认组。
- **边界条件**：
  - 绑定的目标被删除 → 该绑定失效（视为未绑定该目标），不报错；
  - 绑定的目标被停用 → 不投递该目标，其余照常。

**验收标准**：

1. 把会话 X 绑定到目标 A+B → X 的事件同时到 A 与 B；未绑定的会话 Y 的事件只到默认组。
2. 删除目标 A 后再触发 → X 的事件只到 B，且无报错。

---

### 功能点 FR-6：总开关只作用于默认目标组

**功能描述**：沿用既有语义——总开关关闭时，未绑定窗口不发，已绑定窗口照发。

**详细说明**：

- **使用场景**：下班后不想被公共群打扰，但关键会话的提醒要保留。
- **预期结果**：
  - `enabled=false` + 已绑定窗口 → 仍投递到它的目标；
  - `enabled=false` + 未绑定窗口 → 不发。
- **边界条件**：类开关（`notifyComplete` 等）仍是**内容级**过滤，关闭时已绑定窗口也不发（与既有语义一致，不改变）。

**验收标准**：

1. `enabled=false`，会话 X 绑定目标 A → A 仍收到；未绑定的 Y → 默认组收不到。
2. `notifyApproval=false` → 即使绑定了目标，授权事件也不发。

---

### 功能点 FR-7：凭据不回显

**功能描述**：密钥类字段（钉钉加签 secret、飞书签名 secret、自定义请求头里的 token）以**凭据引用**方式保存，界面与日志都不回显明文。

**详细说明**：

- **使用场景**：加签密钥写进 YAML 会随文件流失；写进截图更糟。
- **预期结果**：
  - 配置界面只显示"已配置 / 未配置"；
  - 日志、错误信息、查询接口都不含密钥明文。
- **边界条件**：引用名（环境变量名 / 凭据键名）本身不是秘密，可以显示。

**验收标准**：

1. 目标配置里含 `secretRef` → 界面显示"已配置"，不显示值。
2. 故意让该目标投递失败 → 日志与结果里不出现密钥明文（grep 关键字为空）。

---

### 功能点 FR-8：配置改完即时生效

**功能描述**：保存目标清单后不需要重启 Host，下一次通知即按新清单投递。

**详细说明**：

- **使用场景**：临时加个群，不想重启正在跑的任务。
- **预期结果**：保存 → 立刻触发一次通知 → 按新清单投递。
- **边界条件**：若某项配置被更高优先级层（home patch / 命令行覆盖）压住 → 界面应提示"该值被上层覆盖"，而不是假装保存成功。

**验收标准**：

1. 保存新增目标 → **不重启**，下一次通知同时到新旧目标。
2. 保存删除某目标 → 不重启，下一次通知不再到该目标。

---

### 功能点 FR-9：兼容既有交付

**功能描述**：老配置不改也能跑；语义等价映射到新模型。

**详细说明**：

- **映射规则**：老 `webhookUrl` → 一条「通用自定义」渠道的**默认目标**；老 `bindings`（`sessionId → url`）→ 窗口绑定到该地址对应的目标（地址相同即同一目标）。
- **预期结果**：
  - 只写老配置启动 → 通知照旧发出，报文与既有 v1 契约一致；
  - 老 `bindings.json` 里的绑定继续生效。
- **边界条件**：
  - 老配置与新目标清单**同时存在** → 新清单优先，老配置作为兜底默认目标（并记一条提示）；
  - 回滚：卸载新版本 + 保留 `bindings.json` 即可回到旧行为。

**验收标准**：

1. 用老配置（只有 `webhookUrl` + 老 `bindings.json`）启动 → 通知仍按原样 JSON 发出，报文含 `version/event/message/...`。
2. 老 `bindings.json` 中绑定过的会话 → 仍改道到绑定地址。

---

### 功能点 FR-10：投递结果可查

**功能描述**：每个目标能看到最近一次投递的结果。

**详细说明**：

- **使用场景**：某个群没收到消息时，判断是"没发"还是"发了被拒"。
- **预期结果**：结果含时间、成功/失败、失败原因（HTTP 状态、业务错误码、网络错误）；**保留最近 N 条**（N 在设计中定死）。
- **边界条件**：进程重启后结果可清空（不做持久化要求）。

**验收标准**：

1. 让某目标失败一次 → 查询结果能看到失败原因。
2. 让某目标成功一次 → 查询结果能看到成功与时间。

## 接口契约

### 一、渠道出站报文（插件 → 各 app）

所有渠道统一：`POST <目标地址>`，`Content-Type: application/json; charset=utf-8`，超时/重试/重定向策略沿用既有投递层。

| 渠道 | 请求体形状 | 必需参数 | 成功判定 |
|---|---|---|---|
| 企业微信机器人 | `{"msgtype":"markdown","markdown":{"content":"<正文>"}}` | webhook 地址 | HTTP 2xx **且** `errcode === 0` |
| 飞书自定义机器人 | `{"msg_type":"text","content":{"text":"<正文>"}}` | webhook 地址；可选签名 secret | HTTP 2xx **且** `code === 0`（无 code 字段时按 HTTP 判定） |
| 钉钉机器人 | `{"msgtype":"markdown","markdown":{"title":"<标题>","text":"<正文>"}}` | webhook 地址；可选加签 secret | HTTP 2xx **且** `errcode === 0` |
| Slack Incoming Webhook | `{"text":"<正文>"}` | webhook 地址 | HTTP 2xx |
| Discord Webhook | `{"content":"<正文>"}` | webhook 地址 | HTTP 204/2xx |
| 通用自定义 | 既有 v1 契约原样 JSON（`version/event/message/title/toolName/goal/sessionId/workspace/at/source`） | 任意 http(s) 地址；可选自定义请求头 | HTTP 2xx |

**加签实现口径**（设计细化，需求先定"必须有"）：

- 钉钉：`timestamp` + `sign = base64(hmacSHA256(secret, timestamp + "\n" + secret))`，拼进 query；
- 飞书：`timestamp` + `sign = base64(hmacSHA256(timestamp + "\n" + secret, ""))`（按飞书文档口径）。
- 两者都必须以**凭据引用**取 secret（FR-7），不得写进普通配置字段。

### 二、目标记录的字段契约

| 字段 | 类型 | 必填 | 说明 | 默认值 |
|---|---|---|---|---|
| `id` | string | 是 | 目标标识（稳定、唯一、可读） | 无 |
| `name` | string | 是 | 人看的名字（如"项目群-企微"） | 无 |
| `channel` | string | 是 | `wecom` / `feishu` / `dingtalk` / `slack` / `discord` / `custom` | 无 |
| `url` | string | 是 | 该渠道的 webhook 地址（http/https） | 无 |
| `secretRef` | string | 否 | 加签密钥的**凭据引用名**（仅 `feishu` / `dingtalk` 用） | 空 |
| `headers` | object | 否 | 自定义请求头（仅 `custom` 用） | `{}` |
| `enabled` | boolean | 否 | 是否启用 | `true` |
| `events` | string[] | 否 | 关心的事件类型；**空数组 = 全收** | `[]` |
| `isDefault` | boolean | 否 | 是否属于默认目标组 | `false` |

`events` 取值：`turn/end`、`approval/asked`、`ask_user_question`、`goal/*`。

### 三、Host Service（供其他插件）

既有服务 `dshNoticeWebhook` 的 `bind(sessionId, url)` 升级为可绑多目标，同时**保留旧签名**：

| 方法 | 说明 |
|---|---|
| `bind(sessionId, url)` | 旧签名：按地址定位/创建目标并绑定（兼容 FR-9） |
| `bindTargets(sessionId, targetIds[])` | 新签名：把窗口绑定到若干目标 id |
| `unbind(sessionId)` | 解绑（回落默认组） |
| `listTargets()` | 列出目标（**不含密钥明文**，只给 `secretRef` 与"是否已配置"） |
| `resolve(sessionId)` | 旧签名：返回首个命中目标的地址与来源（兼容） |
| `resolveAll(sessionId)` | 新签名：返回该会话将投递的**全部**目标 |

## 数据契约

| 数据 | 形态 | 持久化 | 说明 |
|---|---|---|---|
| 目标清单 | 目标记录数组（字段见上） | 是（随插件配置持久化） | 界面与 Service 的唯一事实源 |
| 窗口 → 目标绑定 | `sessionId → targetId[]` | 是 | 沿用既有绑定文件的原子写与容错口径 |
| 投递结果 | 每目标最近 N 条 | 否（进程内，重启可清空） | FR-10 |

**版本兼容**：目标清单带 `version`；读到不认识的主版本时按"空清单 + 保留原文件 + 告警"处理（沿用既有坏文件口径）。

## 迁移与兼容

- **默认值兜底**：不写任何新字段时，行为与既有版本一致（老 `webhookUrl` 即默认组里的一个 `custom` 目标）。
- **老绑定文件**：`sessionId → url` 形态继续可读；写入时升级为目标 id 形态（双读单写）。
- **回滚路径**：卸载新版、保留绑定文件；老版本忽略新字段。
- **破坏性变更**：无。既有 `version: 1` 的出站契约保持；渠道报文是**新增**能力。

## 边界（不做什么）

- **不做双向通道**：webhook 回消息不注入会话（沿用既有边界）。
- **不做机器人凭据 / 长连接**：那是 [dsh-im](https://github.com/xmanrui/dsh-im) 的路径（扫码、建应用、权限审批）；本需求只走"给你一条 URL"的入站 webhook。
- **不做富交互卡片模板**：不提供各平台的卡片搭建器；正文是纯文本/markdown 一行。
- **不做消息聚合 / 静默时段**：沿用既有边界。
- **不做凭据管理器**：只**引用**凭据（`secretRef`），不实现密钥的录入/轮换 UI（由 DSH 凭据能力承载）。
- **不做投递结果持久化**：结果留在内存，重启即清（FR-10 已限定）。

## 非功能需求

- **不阻塞会话**：多目标投递不得拖住会话收尾；目标之间互不影响（FR-3 的可用性要求）。
- **失败隔离**：任一目标的任何异常都不得让会话报错，也不得导致其他目标不投递。
- **凭据不进日志**：密钥明文、完整 URL 的 query、`Authorization` 头都不得入日志（沿用既有脱敏口径）。
- **配置校验前置**：非法配置**不落盘**（保存前校验），避免"保存成功但插件起不来"。
- **零第三方运行时依赖**：渠道打包与投递用 Node 内置能力；不为发消息引入 HTTP 客户端库。

## 验收标准（整体）

1. 老配置原样启动 → 通知仍按既有 v1 契约发出（回归）；
2. 界面新增"企业微信机器人"目标 → 收到企业微信形状的报文；
3. 新增第二个目标（Slack）→ 一条通知两个 app 都收到；
4. 把其中一个目标指向不可达地址 → 另一个照常收到，失败目标有原因；
5. 目标只勾"授权" → 完成事件不到它；
6. 把会话 X 绑到 A+B → X 的事件只到 A 与 B；未绑定会话走默认组；
7. `enabled=false` + X 已绑定 → A/B 仍收到；未绑定会话不发；
8. 保存改动**不重启** → 下一次通知即按新清单；
9. 日志与界面里 grep 不到加签密钥明文。
