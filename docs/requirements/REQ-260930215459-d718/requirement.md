# 需求：通知设置页按原型重做并借鉴 dsh-im 图标

> **TL;DR**：把「设置 → 通知」按**已确认的原型**重做（品牌色图标、按渠道分组、数量徽标、默认组分组），
> 图标直接借鉴 dsh-im 的现成 logo；同时把每个渠道的配置**收窄成只填 key**（URL 前缀内置），
> 并给每个渠道一个**可点击的官方配置说明**入口。
> **判定标准**：六项 FR 各自带回执证据，且 `npm test` 全绿 + 活体插槽可查（见文末）。

- **REQ id**：REQ-260930215459-d718
- **类型**：feature
- **来源**：验收现场反馈——「prototype.html 没按原始实施」+「dsh-im 里有图标，直接借鉴过来」+「对应 app 的前置配置只要填 key，而且要有点击查看官方配置说明的页面」

## 产品定义

一句话：**让「设置 → 通知」长成原型的样子的同时，把配置成本从"粘贴整条 webhook URL"降到"只填一个 key"，并在页面上就能看到官方怎么拿这个 key。**

## 用户与角色

| 角色 | 关心什么 | 本需求给他的变化 |
|---|---|---|
| 首次配置的普通用户 | "我只有一个机器人 key，别让我拼 URL" | 只填 key；旁边就有官方获取步骤 |
| 多目标用户 | "哪个渠道配了几个、哪个是默认" | rail 按渠道分组 + 数量徽标 + 默认徽标 |
| 宿主插件开发者 | 可嵌入选择器样式与设置页一致 | 选择器复用同一套图标与徽标（不改契约） |
| 维护者 | 图标不能有版权/来源问题 | logo 借鉴自 dsh-im（已核对其 THIRD_PARTY_NOTICES），来源记入文档 |

## 边界

**做**：

- 目标页与会话绑定页**按原型排版**（按渠道分组、数量徽标、默认组分组、「+ 新增目标」）
- 六个渠道图标换成 dsh-im 的品牌 logo（内联 SVG，不引外链/不加载远程资源）
- 三个"app 渠道"（企微/钉钉/飞书）**只填 key**，URL 由 Host 按渠道前缀组装；Slack/Discord/自定义仍填完整 URL
- 每个渠道一个**可点击的官方配置说明**入口（站内浮层，含步骤与"去哪拿 key"）
- **数据模型扩展与迁移**（因选 B）：目标增 `key`/`secret`，`targets.json` v1 → v2，旧文件按前缀反解 key（反解失败则保留 url 直投）

**不做**（没写进边界的即本次不做）：

- **不改出站报文与加签口径**（六渠道各自形状、业务码判定、钉钉/飞书签名串一律不动）；`bindings.json` 不动；Host Service 方法签名与版本不动
  - **例外（2026-09-30 用户裁定，并入本需求）**：**飞书**渠道的**报文形状**由纯文本改为 `interactive` 卡片（FR-9）；
    飞书的**加签串算法与业务码判定不变**，其余五个渠道的报文**一字不动**
- 不做渠道接入方式的扩展（不加新渠道、不改各平台鉴权流程）
- 不做主题跟随/暗色适配以外的视觉体系改造（只对齐原型，不重做设计系统）

## 功能点

- **FR-1: 渠道图标改用品牌 logo**

  六处图标（企微/飞书/钉钉/Slack/Discord/通用）改用 dsh-im 的品牌 logo 内联 SVG；保留品牌色；
  图标组件统一签名 `({ size }) => element`，供 rail、目标卡、选择器三处复用。不引入远程图片、不加新依赖。

- **FR-2: 目标表单只填 key**

  企微填 `key`、钉钉填 `access_token`（+ 可选加签 `secret`）、飞书填 hook `token`；插件按渠道前缀组装完整地址。
  Slack / Discord / 通用自定义保持"填完整 URL"。编辑既有目标时，从已存 URL 反解出 key 回填，反解失败则退化为显示完整 URL 可编辑。

- **FR-3: 每渠道的官方配置说明入口**

  详情卡内每个渠道提供「怎么拿 key」入口：点击展开站内说明（步骤 + 该渠道机器人配置页的官方地址），
  不要求用户离开当前页面去找；说明内容按渠道各自编写，写清"在哪建机器人、复制哪个字段、加签密钥怎么开"。

- **FR-4: 目标页按原型实现**

  左栏改为：顶部「全部目标」+ 按渠道分组（每组图标 + 名称 + 数量徽标）+「+ 新增目标」+「默认组」分组（列出默认目标并标「默认」徽标）；
  右栏保持详情卡（名称/渠道/地址/密钥/关心事件/默认组/保存·测试·停用·删除/最近投递）。
  视觉规格以 `prototype.html` 帧 1 为准。

- **FR-5: 会话绑定页按原型实现**

  按 `prototype.html` 帧 3：表格列（会话 / 绑定的目标 chips / 操作），悬空引用标红并提示回落默认组，
  解绑二次确认。与目标页共用同一套图标与徽标样式。

- **FR-6: 目标存 key，Host 组装 URL（含迁移）**

  `TargetRecord` 增加 `key`（app 渠道必填）与 `secret`（可选）；`targets.json` 升到 v2，写入时**同时落派生出的 `url`**。
  读 v1 文件时按渠道前缀反解 key：成功则升级为 v2；失败则该条保留 url 原样直投并记 warn（**双读**，不丢目标）。
  Host 侧由渠道适配器负责 `composeUrl(target)`；**出站报文与加签口径一字不改**。
  受新数据模型影响的既有用例允许按新契约更新，但**每处改动都要在测试报告里说明理由**，不得悄悄放宽断言。

- **FR-7: 通知报文带会话上下文**

  每条通知在原有事件文案之外，追加：本地时间、会话标题与会话短 id、工作区、**本轮用户输入摘要**
  （取本轮最后一条非 goal 注入的 `user/message`）、事件专属详情（等待回答→问题文本；等待授权→工具名；
  目标终态→目标描述 + 状态 + 轮次）。目标是「不切回 DSH 也能判断这条通知该不该管、去哪里管」。

- **FR-8: 报文内容可配置**

  FR-7 的每一项都能在插件 config 里开关与调参：字段集合与顺序、摘要长度（`0` = 不带）、
  工作区显示形态（目录名 / 全路径）、时间格式；并提供整段**自定义模板**（占位符替换）覆盖默认拼装。
  **默认值等于 FR-7 的全量形态**，不配置时行为与配置齐全时一致。

- **FR-9: 飞书发交互式富卡片（一级：卡片 + 跳转按钮）**

  飞书渠道由 markdown 文本改为 `interactive` 卡片：事件作为带颜色的标题，会话 / 工作区 / 摘要作为分栏字段，
  底部一枚**跳转按钮**「打开 DSH」（`dsh://open`，已核查 App 仅支持该形式）。
  **只做出站**：不做回调、不做「在聊天里审批 / 回答」——平台侧自定义机器人不支持回调，
  真交互需要自建应用 + 公网可达地址，本轮明确不做。其余渠道本轮保持既有报文不变。

## 决策（已定：B · Host 组装）

**用户裁定（2026-09-30）：选 B。** 目标里存 `channel + key`（+ 可选 secret），**URL 由 Host 在投递时组装**。

这是**推翻**本需求初稿"后端契约零变更"边界的一次范围变更，代价如实列出：

| 影响面 | 要改什么 | 兼容要求 |
|---|---|---|
| 数据模型 | `TargetRecord` 增加 `key`（必填，app 渠道）与 `secret`（可选）；`url` 从"用户填的输入"变成**由 key 推导的派生值** | `targets.json` 版本 1 → 2；**旧文件（只有 url）必须能读**——读时按渠道前缀**反解出 key**，反解不出则该条保留 url 直投（双读） |
| RPC 投影 | `GET /state` 与写端点回/收 `key` 与 `secret`；密钥口径不变（`secret` 只回"是否已配置"，`key` 属于地址的一部分可回显） | 老页面/老调用方传 url 时仍接受（兼容解析） |
| 渠道打包 | `buildRequest` 由 `target.url` 改为 `channel.composeUrl(target)` + `target.secret` | **出站报文与加签口径完全不变**（这是硬边界，见「不做」） |
| 迁移 | 首次读到 v1 文件时按前缀反解 key；反解成功则落 v2，失败则保留原样并记 warn | 卸载/回滚：v2 文件仍带 `url` 字段（派生值落盘），故**旧版本可继续读**（回滚不丢投递能力） |

**仍未变的硬边界**：出站报文（六渠道各自形状与业务码判定）、加签算法、Host Service 方法签名与版本、
观测口径（最近投递）全部不动；`bindings.json` 不动。
